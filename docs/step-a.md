# STEP A — 簡易前段階

ステータス: **方針ドラフト**  
位置づけ: [STEP B（施設向け検証プロトタイプ）](prototype-facility-trial.md) より簡易・実装容易な前段階。  
本製品（[STEP C](product/vision.md)）の前に、**稼働する最小システム**で技術・流れを検証する。

方針: **Rails ＋ Android**。実際に動くものを vibe コーディングで **おおよそ 3 日以内** に作る。  
料金体系は STEP A では持たないが、将来の料金徴収を不可能にしない。  
ユーザ登録・Android APK 更新などの基本仕組みは、隣接プロジェクト `../tanagrid` と同型でよい。

---

## 1. 目的

1. 録音 → 文字起こし → AI 補正 → 回顧録 PDF、という一連の流れを **実際に動く形** で通す。
2. 施設向け（STEP B）や本製品（STEP C）へ展開するとき、**モデル分割やテナント化が不可能でない** 構成にしておく。
3. 高速プロトタイピングのため、役割を分離せず **1 User に集約** して実装コストを下げる。

---

## 2. スコープ／非スコープ

| 区分 | 内容 |
| --- | --- |
| スコープ（STEP A） | Rails サーバ ＋ Android。User ログイン、Web マイページ、QR セッション、音声・画像収集、文字起こし、AI 補正、回顧録 PDF、Admin、APK 更新の最小経路 |
| 非スコープ（STEP B 以降） | 施設テナント、職員／入居者／家族の役割分離、同意管理の本格化、月初バッチ日記、複数施設運用 |
| 非スコープ（STEP C） | 本製品の課金プラン（demo/free/paid/premium）、自叙伝ギフト製品、プレミアム対話など |

### 2.1 ユーザモデル（高速プロトタイピング）

STEP A では次を **同一の User** とする（役割は分けない）。

| 概念上の役割 | STEP A での扱い |
| --- | --- |
| 家族ユーザ | User |
| 施設ユーザ（職員） | User（同一） |
| 話者（入居者） | User（同一） |

Web マイページも Android ログインも、この User を使う。  
`AdminUser` は User と別（`../tanagrid` と同様）。

将来 STEP B で施設・職員・入居者・家族へ分割できるよう、セッション・メディア・生成物は **User に紐づくが、後から resident / facility 等へ付け替え可能な形** を意識する（過剰設計はしない）。

---

## 3. 検証したいこと

1. 3 日程度の vibe コーディングで、E2E（録音〜PDF）が通るか
2. QR 起動セッション → 音声・画像アップロードが実用速度か
3. クラウド ASR の文字起こし精度が、続く補正で使える水準か
4. AI 補正＋回顧録 PDF の品質が「見せられる」最低ラインか
5. tanagrid 流のユーザ登録・APK 更新流用が、このドメインでも足りるか
6. 1 User 集約でも、STEP B への分割余地を残せるか

---

## 4. 必要機能

### 4.1 必須

| 機能 | 内容 |
| --- | --- |
| Rails サーバ | API ＋ Web（マイページ）＋ Admin。ジョブ（文字起こし・補正・PDF） |
| Android アプリ | User ログイン、QR によるセッション開始、音声・画像の収集と送信 |
| User 登録・認証 | Web／Android。基本仕組みは `../tanagrid` と同型でよい |
| Web マイページ | ログイン後の画面。ユーザ基本情報の入力（**テキストボックス 1 つで可**） |
| QR セッション開始 | スキャンでセッションを開始し、以降の音声・画像を当該セッションへ紐付け |
| 音声・画像アップロード | サーバ／オブジェクトストレージへ保存 |
| 文字起こし | サーバ側ジョブ。音声 → テキスト |
| AI 補正 | 文字起こし文のサーバ側 AI 補正（誤変換・読みやすさ） |
| 回顧録 PDF | 収集・補正済み文書から AI で回顧録等を生成し PDF 化 |
| Admin 画面 | システム管理用。`AdminUser` は User と別（`../tanagrid` と同様） |
| APK 更新 | 配布・更新の基本仕組みは `../tanagrid` と同型でよい |

### 4.2 あると楽

| 機能 | 内容 |
| --- | --- |
| 処理ステータス表示 | マイページまたは Admin で「文字起こし中／補正中／PDF 完了」 |
| 生成 PDF のマイページ閲覧・ダウンロード | 家族視点での受け取り体験の確認 |
| セッション一覧 | いつ録ったか・何件あるかの最小一覧 |
| プロンプトの Admin 編集 | 補正・回顧録用プロンプトをコード外で調整 |

### 4.3 後半

| 機能 | 内容 |
| --- | --- |
| 役割・エンティティ分割の下地 | Facility / Staff / Resident / Family への移行を見据えたリネーム・外部キーの余地 |
| 料金の受け皿 | プラン・課金は実装しないが、User や契約単位を後から足せる余白（無理に課金テーブルは作らない） |
| 同意・監査の最小記録 | STEP B 向けに、録音・生成 AI 利用の記録を後付けしやすいログ |

## 5. 技術・構成メモ

```text
┌──────────────────┐     ┌─────────────────────────────┐
│ Android           │     │ Web（マイページ）              │
│ ログイン・QR      │     │ Rails views で可               │
│ 音声・画像収集     │     │ User 基本情報（テキスト 1）     │
└────────┬─────────┘     └──────────────┬──────────────┘
         │ JSON API                      │ HTML
         ▼                               ▼
┌─────────────────────────────────────────────────────┐
│ Rails                                               │
│ User / AdminUser / Session / Media / Transcript     │
│ ActiveJob: 文字起こし → AI 補正 → 回顧録 PDF         │
│ Admin・APK 更新（tanagrid 同型）                      │
└───────────────┬───────────────────┬─────────────────┘
                │                   │
                ▼                   ▼
        Object Storage        ASR / LLM API
```

| 項目 | 方針 |
| --- | --- |
| 期間 | 稼働システムを **おおよそ 3 日以内**（vibe コーディング） |
| スタック | Rails（サーバ）＋ Android |
| 認証 | User（一般）と AdminUser（管理）を分離 |
| 参照実装 | ユーザ登録・APK 更新は `../tanagrid` を踏襲 |
| 料金 | STEP A では不要。将来の徴収を不可能にしない程度の余白のみ |
| STEP B 接続 | 役割分離・施設テナントは後段。データ紐付けが User 一択で硬直しないこと |
