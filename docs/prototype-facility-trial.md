# 施設向けプロトタイプ試験運用案（語り継ぎ・検証版）

段階: **STEP B**  
前段階: [STEP A（簡易前段階）](step-a.md)  
本製品への位置づけ: 将来の「語り継ぎ」本製品（[STEP C](product/vision.md)）への現場データと運用知見を得る検証装置。

ステータス: **試験運用企画**  
目的: 本格製品の前に、福祉施設での日々の聞き取り・蓄積・家族共有を通じて技術・運用・価値を検証する。  
対象技術: **Rails（サーバ）＋ Android（職員用）**。家族閲覧は当面 Web（Rails）で足りる。  
前提: AI 自動処理を主とし、少人数（例: スタッフ 2 名＋施設現場）で回せる構成。

料金プラン・製品ロードマップは本ドキュメントの対象外とする。

---

## 1. コンセプト

施設に入居する高齢者を対象に、**施設職員が日常業務の延長で短時間の会話を行い**、音声・写真を蓄積する。

| 項目 | 内容 |
| --- | --- |
| 話者 | 施設入居者 |
| 収集者 | 施設職員（Android アプリ） |
| 識別 | 入居者ごとの **QR コード**（スキャンでセッション開始） |
| 頻度 | 毎日、または 2〜3 日に 1 回、**約 10 分** |
| サーバ処理 | アップロード → 自動文字起こし → 月初の文章生成 |
| 生成物 | **回顧録風**（過去の記憶）と **日記風**（最近の日常） |
| 閲覧 | 家族のマイページ |
| 拡張 | 誕生日・クリスマス等の雑誌的読み物、希望時の自叙伝製本 |

## 2. 実現可能性（結論）

**条件付きで実現可能。**

| 領域 | 判定 | 補足 |
| --- | --- | --- |
| 基本プロファイル収集 | 可能 | Rails 管理画面＋職員アプリで十分 |
| QR 起動セッション | 可能 | Android のカメラ QR → 入居者 ID 解決 → 録音画面 |
| 音声・写真アップロード | 可能 | 署名付き URL 等でオブジェクトストレージへ |
| 自動文字起こし | 可能 | クラウド ASR。日本語・施設ノイズは精度検証が必須 |
| 月初の回顧録／日記生成 | 可能 | LLM。職員または運営による軽い確認を推奨 |
| 家族マイページ | 可能 | Rails の認証付き Web で先行 |
| イベント雑誌・製本 | 試験後半で可能 | 自動 PDF → 外注印刷。初回は手動オペでも可 |
| 認知予防の「客観的証明」 | **本サービスの単独では困難** | 下記 §7。効果の「示唆」収集までは設計可能 |

以前整理した **AI 中心・少人数** の条件とも整合する。職員が「聞きに行くプロ」ではなく「10 分の会話オペレータ」になる点が、コスト上の肝である。

## 3. 試験運用で検証したいこと

1. 職員が **10 分会話を継続できるか**（業務負荷・定着率）
2. QR 起動が現場で速くて誤認が少ないか
3. 施設の音環境で ASR が実用か
4. 回顧録／日記の文章が家族に受け入れられるか
5. 同意・プライバシー運用が施設ルールに合うか
6. （任意）簡易スケールでの気分・コミュニケーション変化の前後比較

## 5. 必要機能（試験運用 MVP）

### 5.1 必須

| 機能 | 内容 |
| --- | --- |
| 施設・職員アカウント | 施設単位のテナント。職員ログイン |
| 入居者プロファイル | 氏名、生年月日、家族構成、学歴、職歴、趣味、注意事項（アレルギー等は任意） |
| 同意管理 | 録音・家族共有・生成 AI 利用の同意記録（紙スキャン添付可） |
| QR 発行・印刷 | 入居者 ID を含む QR。名札・ベッドサイド用 |
| セッション | QR 読取 → 入居者確定 → 録音開始／停止 → 写真追加 → 送信 |
| オフライン耐性（簡易） | 回線不良時は端末に一時保存し、復帰後アップロード |
| アップロード | 音声・写真をサーバ／オブジェクトストレージへ |
| 文字起こしジョブ | 完了後にテキスト表示（職員は修正できなくても試験初期は可） |
| 月初バッチ | 前月分を結合し「回顧録」「日記」を生成・保存 |
| 家族マイページ | 招待リンクまたはメール登録。当該入居者のみ閲覧 |
| 監査の最小ログ | 誰がいつセッションしたか |

### 5.2 あると試験が楽

| 機能 | 内容 |
| --- | --- |
| 会話ガイド | 10 分用の質問カード（過去／今日の気分／季節） |
| 職員向けダッシュボード | 今日未実施の入居者リスト |
| 文字起こしの軽い修正 | 職員が誤変換だけ直せる |
| プッシュ通知 | 家族へ「今月の日記が届きました」 |
| 生成文の「下書き／公開」 | 施設または運営が公開ボタンを押すまで家族に非表示 |

### 5.3 後半

| 機能 | 内容 |
| --- | --- |
| イベント特集 PDF | 誕生日・クリスマス用の雑誌的レイアウト（写真＋要約） |
| 製本発注 | PDF を印刷会社へ（手動連携で開始可） |
| 簡易アウトカム記録 | 月 1 の観察メモ、既存の施設スケール値の手入力 |

## 6. システム構成案（Rails ＋ Android）

```text
┌──────────────────┐     ┌─────────────────────────────┐
│ Android（職員）   │     │ Web（家族マイページ／管理）   │
│ QR・録音・写真    │     │ Rails views で先行可          │
└────────┬─────────┘     └──────────────┬──────────────┘
         │ JSON API                      │ HTML / API
         ▼                               ▼
┌─────────────────────────────────────────────────────┐
│ Rails（apps/server 相当）                            │
│ 認証・施設テナント・入居者・セッション・同意・生成文   │
│ ActiveJob: 文字起こし / 月初まとめ / PDF              │
└───────────────┬───────────────────┬─────────────────┘
                │                   │
                ▼                   ▼
        Object Storage        ASR / LLM API
        （音声・写真）         （外部クラウド）
```

### 6.1 推奨リポジトリ構成（シンプル）

```text
facility-prototype/   # または monorepo 内 apps/
├─ apps/
│  ├─ server/     # Rails API + Admin + 家族 Web
│  └─ staff/      # Android（Kotlin 推奨）
├─ docs/
└─ compose.yml    # 開発用 DB 等
```

プロトタイプではモノレポ必須ではない。Rails と Android を別リポジトリにしてもよい。

### 6.2 技術方針（試験向けに抑える）

| 項目 | 方針 |
| --- | --- |
| API | Rails `/api/v1`、職員はトークン認証 |
| 家族 Web | サーバサイド HTML で十分（React 必須にしない） |
| 音声 | m4a 等。長時間分割は 10 分想定なら単発で可 |
| ストレージ | S3 互換。Rails はメタデータのみ |
| ASR | クラウド API 1 社に固定し、精度を測る |
| LLM | 月初バッチのみ。プロンプトは「事実に忠実／脚色しすぎない」 |
| QR ペイロード | 推測困難なトークン（連番 ID のみは避ける） |

### 6.3 論理データ（最小）

| エンティティ | 主な属性 |
| --- | --- |
| Facility | 名称、契約試験フラグ |
| StaffUser | facility_id、認証 |
| Resident | プロファイル、qr_token、同意フラグ |
| FamilyUser | 閲覧権限（resident 紐付け） |
| Session | resident_id、staff_id、started_at、duration |
| MediaAsset | session_id、kind(audio/photo)、storage_key |
| Transcript | session_id、text、status |
| MonthlyStory | resident_id、year_month、kind(memoir/diary)、body、status |
| EventZine | 任意。イベント種別、PDF キー |

## 7. 基本フロー

### 7.1 日々のセッション

```text
職員が QR を読む
  → 入居者プロフィール表示（確認）
  → ガイド質問（任意）
  → 約 10 分録音 ＋ 必要なら写真
  → 送信
  → サーバが文字起こしジョブ投入
  → 完了（職員画面で「処理中／完了」）
```

### 7.2 月初まとめ

```text
バッチ（毎月 1 日など）
  → 前月の Transcript を時系列結合
  → プロファイル（学歴・職歴等）をコンテキストに付与
  → LLM:
       A. 過去想起が主 → 回顧録風
       B. 施設の今日・今週の話が主 → 日記風
  → MonthlyStory を draft 保存
  → （推奨）施設 or 運営が公開
  → 家族マイページに表示
```

分類が曖昧な発話は「日記」に寄せるか、両方に短く要約するルールを先に決める。

### 7.3 イベント読み物

```text
誕生日トリガ or 手動
  → 直近 N か月の日記・回顧録・写真を抽出
  → 雑誌風 PDF 生成
  → 施設が印刷 or 家族がダウンロード
```

## 9. 認知機能低下予防を「客観的に証明」できるか

### 9.1 結論

**このプロトタイプサービス単体の運用ログだけでは、医学的・科学的に「予防効果がある」と客観証明するのは難しい。**  
一方で、**回想法（remiscence）には一定の研究蓄積があり**、施設での定期的な回想会話は認知・気分・QOL に対し **小〜中程度の改善や維持が報告されることがある**。効果は介入頻度・期間・対象・測定指標に強く依存し、長期持続も限定的とされることが多い。

代表的な示唆（既存研究の傾向）:

- 個人回想法を週複数回・十数週続ける RCT で、全般的認知や記憶、QOL などに有意差が出た報告がある  
- メタ分析でも認知・記憶・うつ・QOL への効果が示唆される一方、実行機能などには効果が弱い／フォローアップが限られる  
- **「本アプリを使えば予防できる」という因果の証明**には、対照群・事前定義のアウトカム・倫理審査を伴う研究デザインが必要  

### 9.2 試験運用でできること／できないこと

| できること | できないこと（過大表明の禁止） |
| --- | --- |
| セッション継続率・会話時間の計測 | 「認知症を予防できる」と広告・説明する |
| 家族・職員の満足度・受容性の調査 | 診断・治療の代替であると謳う |
| 施設既存スケール（例: 観察記録）との **探索的な前後比較** | ランダム化なしの結果を「証明」と呼ぶ |
| 将来の正式研究（大学・医療機関連携）のプロトコル草案づくり | 薬機法・景表法に抵触しうる効能表現 |

### 9.3 将来「証明に近づける」なら必要な条件（プロトタイプ外だが記録）

1. 研究計画書と倫理審査  
2. 対照群（通常ケアのみ）または待機リスト  
3. 事前に決めた指標（例: MMSE / MoCA、うつ尺度、QOL）  
4. 介入プロトコルの固定（週何回・何分・質問セット）  
5. 十分なサンプルサイズと追跡期間  
6. 利益相反・同意の明確化  

プロトタイプ段階の推奨メッセージ:  
**「過去の記憶に触れる会話を、記録と家族共有つきで日常化する仕組みの検証」**  
であり、医療効能の主張は行わない。

## 10. 施設試験に必要な現場条件

| 項目 | 推奨 |
| --- | --- |
| 規模 | まず **1 施設・入居者 5〜15 名** |
| 期間 | **8〜12 週**（月初まとめを 2 回以上回す） |
| 職員 | 担当 1〜2 名を固定し、1 人あたり1日数名まで |
| 端末 | 業務用 Android 1〜数台（個人スマホ混在はセキュリティ上非推奨） |
| Wi-Fi | アップロード可能なエリアを確保 |
| 同意 | 入居者本人および必要な場合は家族・施設 eth ics に沿う手続き |
|  Quiet な場所 | 食堂中央より、個室・静かなコーナーが望ましい（ASR 精度） |

## 11. リスクと対策

| リスク | 対策 |
| --- | --- |
| 職員が続かない | 未実施リスト、所要 10 分厳守、質問カードで迷いを減らす |
| 誤った入居者で録音 | QR 後に氏名の目視確認を必須画面に |
| ASR 誤変換が多い | 固有名詞辞書（家族名・地名）、職員の軽修正 |
| LLM の脚色・事実誤り | 公開前確認、根拠セッションへのリンク |
| プライバシー漏洩 | 施設テナント分離、家族は当該入居者のみ、音声の無制限ダウンロード禁止 |
| 「医療効果」と誤解 | UI・説明文に効能を書かない。研究は別契約 |

## 14. まとめ

- **日々の QR セッション → 自動文字起こし → 月初の回顧録／日記 → 家族閲覧** は、Rails＋Android＋クラウド ASR/LLM で試験運用可能。  
- イベント雑誌・製本は PDF 自動化＋外注で後段追加可能。  
- **認知低下予防の客観的証明は、本試験だけではできない。** 回想法の既存エビデンスを踏まえた「可能性の探索」と、将来の正式研究設計までは視野に入れられる。  
- まずは **1 施設・少人数・効能を謳わない** ことが、安全で学びの多い始め方である。
